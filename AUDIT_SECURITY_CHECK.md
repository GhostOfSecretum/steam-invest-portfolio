# SECURITY-CHECK: Steam Invest Portfolio

**Дата:** 6 июля 2026
**Аудит выполнен моделью:** Fable 5
**Тип аудита:** операционная безопасность (секреты, конфигурации, зависимости, инфраструктура)
**Режим:** только чтение — код проекта не изменялся.

---

## Резюме

Репозиторий в целом гигиеничен: `.env` корректно исключён из git и docker-образа, в отслеживаемом коде захардкоженных секретов не найдено, история git чистая. Основные риски: **реальные живые секреты в локальном `.env`** (включая строку сессии Telegram, дающую полный доступ к аккаунту), **критические/высокие уязвимости в зависимостях** (protobufjs, Electron, axios), **запуск контейнера от root** и **неаутентифицированные API ручных портфелей** при биндинге сервера на все интерфейсы без HTTPS.

---

## Находки

### Критическая серьёзность

#### K-1. Живая строка сессии Telegram в `.env`
- **Файл:** `.env` (строка 8)
- **Описание:** `TELEGRAM_SESSION=1AgAOMTQ5...` (значение замаскировано) — это действующая MTProto-сессия пользовательского аккаунта Telegram. Её компрометация даёт **полный доступ к аккаунту** (чтение переписки, отправка сообщений, управление аккаунтом), а не только к API. Там же лежат реальные `TELEGRAM_API_ID=3837...` и `TELEGRAM_API_HASH=6e67...`. Файл не отслеживается git (проверено `git ls-files .env` — пусто; `git check-ignore -v` подтверждает правило `.gitignore:3`), история git по `.env` пустая, но файл хранится в открытом виде в папке `Downloads` и автоматически читается любым инструментом/агентом, работающим с проектом.
- **Рекомендация:** считать сессию потенциально скомпрометированной (она уже была видна инструментам аудита) — отозвать её в Telegram (Settings → Devices → Terminate session) и сгенерировать новую. Для аккаунта, используемого ботом-читателем новостей, лучше завести отдельный некритичный аккаунт. Рассмотреть хранение секретов в менеджере секретов / keychain вместо plaintext-файла.

#### K-2. Критическая уязвимость protobufjs в desktop-клиенте (RCE)
- **Файл:** `desktop/package-lock.json` (транзитивно через `steam-user` → `steam-appticket` → `protobufjs`)
- **Описание:** `npm audit` в `desktop/` сообщает о **critical**-уязвимости «Arbitrary code execution in protobufjs» (GHSA-xq3m-2v4x-88gg) плюс ещё ~10 advisories (code injection, prototype pollution, DoS). protobufjs парсит данные, приходящие от Steam Game Coordinator, то есть обрабатывает внешний ввод.
- **Рекомендация:** обновить `steam-user`/`globaloffensive` до версий с исправленным protobufjs (`npm audit fix`, при необходимости `--force` с проверкой breaking changes) и пересобрать desktop-дистрибутивы.

### Высокая серьёзность

#### В-1. Реальный Steam API key в `.env`
- **Файл:** `.env` (строка 4)
- **Описание:** `STEAM_API_KEY=D688...` (замаскировано) — действующий ключ Steam Web API. Ключ привязан к аккаунту Steam; в истории были случаи использования утёкших ключей для перехвата трейдов (API key scam). Хранится в открытом виде.
- **Рекомендация:** периодически ротировать ключ на https://steamcommunity.com/dev/apikey; после данного аудита ротация желательна.

#### В-2. Устаревший Electron с множеством advisories
- **Файл:** `desktop/package-lock.json`
- **Описание:** установлен `electron 33.4.11`; `npm audit` перечисляет 18 advisories высокой серьёзности для `electron <= 39.8.4` (use-after-free, ASAR integrity bypass, header injection, IPC spoofing и др.). Desktop-приложение открывает WebView со входом в Steam — уязвимости рендерера здесь особенно чувствительны.
- **Рекомендация:** обновить Electron до актуальной мажорной версии (audit предлагает 43.x), пересобрать и перевыложить установщики из `downloads/`.

#### В-3. Уязвимые зависимости серверной части (axios, form-data, qs)
- **Файл:** `package-lock.json` (корень)
- **Описание:** `npm audit --omit=dev`: 4 уязвимости (2 high, 2 moderate). `axios 1.15.2` — 8 advisories (утечка Proxy-Authorization, ReDoS, prototype pollution → MitM); `form-data 4.0.5` — CRLF-инъекция; `qs 6.14.2` (зависимость express) — DoS. axios/form-data приходят транзитивно (telegram-клиент и др.).
- **Рекомендация:** выполнить `npm audit fix` (все исправления доступны без breaking changes) и зафиксировать обновлённый lock-файл.

#### В-4. API ручных портфелей без аутентификации
- **Файл:** `server/index.js` (строки 140–176), `server/services/portfolio.js`
- **Описание:** эндпоинты `POST/DELETE /api/portfolios`, `POST/PATCH/DELETE /api/portfolios/:id/items` и `PATCH /api/portfolio/basis` (для manual-портфелей) не требуют сессии. Любой, кто имеет сетевой доступ к порту 3000, может читать, изменять и удалять все ручные портфели (данные лежат в общем `.data/manual-portfolios.json` без привязки к пользователю). Сервер слушает все интерфейсы (`app.listen(port)` без host), а docker-compose публикует порт наружу.
- **Рекомендация:** для локального MVP — биндить на `127.0.0.1` (или в compose публиковать как `127.0.0.1:3000:3000`); при развёртывании на сервере — добавить `requireAuth` к мутирующим эндпоинтам и привязать manual-портфели к steamId.

#### В-5. Контейнер работает от root
- **Файл:** `Dockerfile`
- **Описание:** нет директивы `USER` — Node-процесс в контейнере выполняется от root. При компрометации приложения (например, через уязвимую зависимость) атакующий получает root внутри контейнера, включая запись в примонтированный `./.data`.
- **Рекомендация:** добавить `USER node` после копирования файлов (образ `node:20-alpine` уже содержит пользователя `node`) и выдать ему права на рабочие каталоги.

### Средняя серьёзность

#### С-1. Cookie сессии без флага Secure, HTTPS не форсируется
- **Файл:** `server/index.js` (строки 35–46)
- **Описание:** `cookie.secure: false` захардкожен — даже при развёртывании за HTTPS-прокси cookie будет передаваться и по HTTP. Сам сервер HTTP-only; `sameSite: 'lax'` и `httpOnly: true` при этом выставлены корректно.
- **Рекомендация:** при продакшен-развёртывании выставлять `secure: true` (например, по `NODE_ENV=production` вместе с `trust proxy`).

#### С-2. Fallback-значение SESSION_SECRET в коде
- **Файл:** `server/index.js` (строка 37)
- **Описание:** при отсутствии переменной используется дефолт `'local-dev-only-change-me'` — предсказуемый секрет позволяет подделывать сессионные cookie. В текущем `.env` задан собственный секрет, но с префиксом `local-dev-...`, что намекает на его использование и за пределами dev.
- **Рекомендация:** в продакшене падать при отсутствии `SESSION_SECRET` вместо дефолта; сгенерировать случайный секрет (например, `openssl rand -hex 32`).

#### С-3. Доверие заголовкам X-Forwarded-* без включённого trust proxy
- **Файл:** `server/services/auth.js` (строки 11–26)
- **Описание:** `resolveBaseUrl()` читает `x-forwarded-proto`/`x-forwarded-host` **безусловно**, даже когда `TRUST_PROXY` не включён. Атакующий может подставить свой Host/X-Forwarded-Host и повлиять на `return_to`/realm OpenID-редиректа (фишинговый сценарий: жертва после логина уходит на хост атакующего). Смягчение: Steam проверяет соответствие return_to и realm, а verifyAssertion идёт на тот же вычисленный baseURL.
- **Рекомендация:** учитывать `x-forwarded-*` только при `TRUST_PROXY=true`, либо всегда задавать `APP_BASE_URL` на сервере (что README/env.example уже рекомендует).

#### С-4. In-memory session store (MemoryStore)
- **Файл:** `server/index.js`
- **Описание:** `express-session` используется с дефолтным MemoryStore, который официально не предназначен для продакшена (утечки памяти, потеря сессий при рестарте, не масштабируется).
- **Рекомендация:** для серверного развёртывания подключить постоянный store (redis/file-based).

#### С-5. Device token в query-параметре URL
- **Файл:** `server/index.js` (строки 324–337)
- **Описание:** `GET /api/desktop/login?deviceToken=...` передаёт долгоживущий (90 дней) токен в URL — он попадает в логи прокси/access-логи и историю браузера. Сам токен сгенерирован надёжно (`crypto.randomBytes(32)`).
- **Рекомендация:** передавать токен в заголовке или использовать одноразовый короткоживущий обменный код.

#### С-6. Пары «6-значный pairing code» без rate limiting
- **Файл:** `server/index.js` (строки 285–297), `server/services/desktop.js`
- **Описание:** `POST /api/desktop/pair` принимает 6-значный код (1 млн комбинаций, TTL 10 минут) без аутентификации и без ограничения частоты запросов — перебор возможен при доступном порте. Успешный подбор даёт device token и вход в аккаунт через `/api/desktop/login`.
- **Рекомендация:** добавить rate limiting (например, `express-rate-limit`) и/или удлинить код.

#### С-7. SOCKS5-прокси xray без аутентификации
- **Файл:** `scripts/generate-xray-config.js` (строки 70–82), `docker-compose.yml`
- **Описание:** генерируемый конфиг xray поднимает SOCKS5 c `auth: 'noauth'` на `0.0.0.0:1080` внутри контейнера. Порт **не публикуется** наружу в compose (доступен только из docker-сети) — поэтому серьёзность средняя, а не высокая. Однако при добавлении `ports:` к сервису xray это стало бы открытым прокси через ваш VPN. Секретов в самом скрипте нет — VLESS UUID/ключи берутся только из env; итоговый `xray/config.json` (содержащий UUID) корректно в `.gitignore`.
- **Рекомендация:** оставить порт непубликуемым; при необходимости внешнего доступа включить auth у SOCKS-инбаунда.

#### С-8. Скрипт оставляет сессию Telegram в `/tmp` на сервере
- **Файл:** `scripts/telegram-session-on-server.sh` (строка 33)
- **Описание:** вывод логина, включая полную строку `TELEGRAM_SESSION`, пишется через `tee` в `/tmp/telegram-session.out` и не удаляется после использования — читаемый артефакт с критичным секретом остаётся на сервере. Также скрипт принимает `TELEGRAM_CODE`/`TELEGRAM_PASSWORD` через переменные окружения (видны в env процесса).
- **Рекомендация:** добавить `trap 'rm -f /tmp/telegram-session.out' EXIT` или использовать `mktemp` с удалением; `scripts/create-telegram-session.js` и `apply-telegram-session.js` сами по себе секретов не содержат.

#### С-9. Лимит тела запроса 50 МБ
- **Файл:** `server/index.js` (строка 34)
- **Описание:** `express.json({ limit: '50mb' })` применяется глобально ко всем эндпоинтам, а не только к inventory-sync — упрощает DoS большими JSON-телами на неаутентифицированных ручках.
- **Рекомендация:** глобально оставить дефолтный лимит (100kb) и повышенный лимит вешать только на `/api/desktop/inventory-sync`.

### Низкая серьёзность

#### Н-1. Отсутствуют security-заголовки
- **Файл:** `server/index.js`
- **Описание:** нет `helmet`/CSP/X-Content-Type-Options; `express.static(rootDir)` раздаёт весь корень проекта, включая `CLAUDE.md` и исходники `*.jsx`. Важно: `.env` при этом **не раздаётся** — `express.static` по умолчанию игнорирует dotfiles (`dotfiles: 'ignore'` → 404), но раздача корня репозитория остаётся плохой практикой.
- **Рекомендация:** добавить `helmet` и раздавать статику из выделенной папки `public/` вместо корня репозитория.

#### Н-2. Инвайт-ссылки приватных Telegram-каналов в `.env`
- **Файл:** `.env` (строка 9)
- **Описание:** `TELEGRAM_CHANNELS` содержит инвайт-хэши приватных каналов (`t.me/+HsAE...`, `t.me/+Z4B8...`) — сами по себе не секреты уровня токена, но дают возможность вступить в приватные каналы.
- **Рекомендация:** учитывать при передаче `.env` третьим лицам.

#### Н-3. `.data/` содержит только рыночные/портфельные данные
- **Файл:** `.data/cache.json`, `.data/portfolio.json`, `.data/manual-portfolios.json`
- **Описание:** директория корректно в `.gitignore` и `.dockerignore`. Токены устройств (`desktop:token:*`) хранятся в `cache.json` в открытом виде — приемлемо для локального файла, но стоит помнить, что бэкап `.data` содержит действующие device-токены.
- **Рекомендация:** без изменений для локального MVP; при переносе на сервер — ограничить права файла (600).

## Положительные находки

- **`.env` не в git:** `git ls-files .env` пуст, `git check-ignore` подтверждает правило (`.gitignore:3`), история git по `.env` пустая — секреты никогда не коммитились, при том что у репозитория есть публичный remote на GitHub.
- **`.dockerignore` корректный:** `.env`, `.git`, `.data`, `node_modules`, `xray/config.json` не попадают в docker-образ несмотря на `COPY . .`.
- **Нет захардкоженных секретов в коде:** grep по всему отслеживаемому коду (`server/`, `scripts/`, `desktop/`) реальных токенов/ключей не нашёл; всё берётся из переменных окружения; `.env.example` содержит только плейсхолдеры.
- **Steam OpenID реализован аккуратно:** проверяются `openid.ns`, `op_endpoint`, префиксы `claimed_id`/`identity`, финальный `claimedIdentifier` валидируется regex-ом на SteamID64; сессия регенерируется при логине (защита от session fixation).
- **Cookie:** `httpOnly: true`, `sameSite: 'lax'`, кастомное имя cookie.
- **Device-токены** генерируются криптографически стойко (`crypto.randomBytes(32)`), pairing-код имеет TTL 10 минут и одноразовый (удаляется после обмена).
- **GitHub Actions безопасен:** единственный workflow `desktop-build.yml` запускается только по `workflow_dispatch`, не использует secrets, нет `pull_request_target`, нет интерполяции недоверенного ввода в `run`-шаги; артефакты — только собранные бинарники.
- **docker-compose:** xray-конфиг с VLESS-ключами живёт в именованном volume и монтируется в xray read-only; наружу публикуется только порт приложения; секреты передаются через `env_file`, а не через `environment` в явном виде.
- **Ошибки сервера** не раскрывают stack trace клиенту (отдаются только `message` и `code`).
